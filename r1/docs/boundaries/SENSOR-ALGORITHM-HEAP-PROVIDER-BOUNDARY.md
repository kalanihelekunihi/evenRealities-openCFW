# Sensor-algorithm heap provider boundary

## Decision

Owner-authorized reduction update (2026-08-14): the twelve Goodix-owned allocator-core entries /
1,126 bytes now compile from independently reconstructed C in `reconstructed/goodix_heap/` and
route to `clean_room_reimplementation_owner_authorized`. The licensed Goodix binary is evidence
only and is not a build input. Exact hashes, recovered contracts, deliberate safety changes, and
tests are recorded in
[`../correlation/GOODIX-HEAP-REDUCTION-CORRELATION.md`](../correlation/GOODIX-HEAP-REDUCTION-CORRELATION.md).
All twenty Goodix-owned allocation/teardown call-site helpers (386 more bytes) now compile from
`reconstructed/goodix_primitives/`, and the 12-byte R1 pool byte-fill compiles there as product
code. Thus none of the 34 rows in this boundary requires an opaque binary build input; the
product fatal path remains an explicit callback policy rather than allocator-internal code.
The historical attribution and ABI analysis below remain the basis for the reconstruction.

The recovered application contains thirteen exact functions, totaling 1,202 executable bytes,
that implement a private heap used by linked sensor algorithms. The component is identified by
its `sensor_algo_mem_fatal, info1: %u` terminal diagnostic, its shared control-pointer slot at
`0x20007C64`, and the direct initialization edge from Goodix-candidate entry `0x0002A090`.

Provenance is resolved. The component is Goodix's `goodix_mem` / `GdMem` memory-pool manager
from the Goodix GH3X2X health-sensor algorithm SDK common DSP support library; R1 carries the
SDK config tag `gh3x2x-v2.23_7ecd2a`, matching the public GH3X2X SDK mirror. The public SDK
header `goodix_mem.h` declares `goodix_mem_init`/`deinit`/`malloc`/`free`/`get_free_size` with
exactly the -1 (null base) / -2 (non-positive size) error contract the R1 init body implements,
and declares `extern void Gh3x2xPoolIsNotEnough(void)` as an integrator-supplied callback.
Instruction-level disassembly comparison against the Goodix common-DSP library object matched
the R1 members: `GdMemInit` (second span of `0x0006DFD6`: 1,024-byte minimum pool, sentinel
`strd` pairs, +0x33&~7 alignment, size<<2 tail encoding), `goodix_mem_init` (null→-1,
size≤0→-2, memset, tail-call `GdMemInit`), `GdMemMalloc` (minimum-8 request, round-4, +8
header, bin split at 1,024, bitmap search, split-if->15, |3 mark, top-chunk fallback,
`Gh3x2xPoolIsNotEnough` on failure), `GdMemFree` (`0x0002D460`), `GdMemRealloc` (`0x0002D5C0`),
unlink (`0x00076A44`), insert (`0x00093E5E`), and `GdMemGetFreeSize` (`0x0006DFCC`).

The Goodix SDK license is restrictive (BSD-style, use limited to Goodix ICs, no reverse
engineering of binary forms) and the module ships binary-only. The component was formerly
censused under `unknown_sensor_algorithm_heap_provider_candidate`. Under the later
owner-authorized full reduction, the twelve allocator-core bodies retain the
`goodix_gh3x2x_candidate` provenance family while routing to the local reconstruction. The later
call-site pass places all twenty Goodix consumer helpers in the generated local-symbol map too.

Two members are integrator-authored R1 glue, not Goodix code: `0x0002E952`, the
integrator-supplied `Gh3x2xPoolIsNotEnough` handler
(logs `sensor_algo_mem_fatal, info1: %u`, flushes, then loops forever), and `0x00092B60`, the
12-byte product byte-fill (memset) used by `goodix_mem_init` for pool clearing. Both route to
`r1_product_specific`; the fatal policy remains `clean_room_behavior_only`, while the byte-fill
now routes to `clean_room_reimplementation_owner_authorized` and compiles locally.

The exact census is generated by
`../../tools/evidence/summarize_r1_sensor_algorithm_heap.py`.

## Recovered data structure and behavior

The initializer receives fixed SRAM base `0x2003024C` from the Goodix-candidate initialization
path and a caller-supplied pool size. It rejects a null base, non-positive size, and pools of 1,024
bytes or less, clears the supplied pool, stores its base through `0x20007C64`, creates two circular
free-list sentinels, aligns the first block to eight bytes, and creates one tail block.

The recovered contract is:

- 44-byte allocator control prefix;
- two bitmap-selected, size-ordered free-list bins;
- minimum request of eight bytes and four-byte request rounding;
- eight-byte block header and low two status bits in the encoded size word;
- boundary records used for backward coalescing;
- split only when at least 16 bytes remain; and
- allocation failure routed into the terminal diagnostic rather than returned as ordinary
  recoverable pressure.

These details are the compatibility basis for the owner-authorized independent reconstruction and
its tests; they do not make the reconstructed C Goodix source.

## Excluded source matches

This component is not FreeRTOS `heap_4`. The application's actual authenticated FreeRTOS-Kernel
10.0.0 `heap_4` is separately source-routed and uses its characteristic single address-ordered
free list, allocated-bit rules, scheduler suspension, and 51,200-byte heap. The six-byte body at
`0x00042D1C` happens to share instruction bytes with `xTaskGetCurrentTaskHandle`, but it loads
`0x20007C64`, not `pxCurrentTCB` at `0x2000781C`; identical generic accessor bytes do not establish
common ownership.

It is also not TLSF v3.1. The pinned Matthew Conte TLSF source elsewhere in this repository uses
the substantially larger two-level segregated-fit control structure and mapping rules. The R1
component instead has a 44-byte control prefix and only two bins. No TLSF source is admitted for
this boundary.

## Integration rule

The restrictive Goodix binary remains excluded. The owner-authorized C implementation must retain
the recovered geometry and behavior tests, explicit exhaustion policy, offset-safe host layout,
and per-entry ownership mapping. `Gh3x2xPoolIsNotEnough` remains product policy (`0x0002E952`),
and the pool-clearing byte-fill (`0x00092B60`) remains ordinary locally compiled R1 product code.
All twenty Goodix call-site helpers are locally compiled and exact-address source-mapped. Reconstructing the
heap does not by itself enable a biometric path; every dependent algorithm closure must separately
be source-owned and verified before runtime binding.

The evidence parser is read-only. The reconstructed allocator operates only on caller-supplied
memory and performs no hardware access, firmware mutation, or code signing.
