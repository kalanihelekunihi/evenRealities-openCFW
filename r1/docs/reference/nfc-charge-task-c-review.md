# R1 NFC/charging task lifecycle and worker in C

`native_nfc_charge_task.c` supplies the worker at stock 0x924f4, create at 0x45fd4 and stop at 0x45fbc. The authenticated attributes and watchdog label identify the worker as `nfc_charge`; the existing descriptive worker API remains `r1_system_task_plan_startup`. This implements the software lifecycle/loop and exposes its missing hardware children, rather than supplying no-op implementations.

The normal build compiles 808 units (726 application, 82 bootloader). Application imports increase from 69 to 73 because these four real dependencies are now explicit: `r1_battery_initialize_000912a8`, `r1_battery_periodic_schedule_00091174`, `r1_pmic_late_init_plan_build` and `r1_nfc_charge_task_plan_build`. R1 source checking and strict bootloader linking pass. Global checking retains the unrelated G2 unlisted `resident_rom_thumb_set.S` failure. Final application linking and the manager topology remain open.

The worker waits on startup sync group 1, creates a 50-entry queue of 44-byte messages, publishes its handle before checking failure, calls all three hardware initialization stages, publishes startup acknowledgement and registers watchdog `nfc_charge` with timeout 10000. Each iteration arms the live watchdog handle, waits on mask 0x00ffffff with zero options and infinite timeout, disarms the live handle, dispatches only when unsigned `flags - 1 < 0x7fffffff`, then feeds the live handle. Every arm/disarm/feed reloads its volatile owner, including after provider mutations. Zero, high-bit status errors and all-ones status do not dispatch; they still reach the feed stage.

Creation uses the existing `r1_battery_thread_handle` owner, despite that legacy name, and publishes the new handle before failure handling. Stop loads the handle once, calls termination if nonnull and clears the owner after the provider returns, even if it failed or changed the owner. A separate eight-byte lifecycle prefix contains relocatable create/stop callbacks. The queue and watchdog cells at stock 0x2000663c/0x2000662c have new source owners; all three accessed handle words start at zero in authenticated decoded RAM.

Attributes retain name `nfc_charge`, 112-byte TCB reservation, 4096-byte stack, priority 28, TrustZone module 1 and zero remaining fields. Both reservations are aligned to eight bytes. The static attributes are checked against the stock nine-word record at 0x99264. This is allocation/metadata evidence, not proof of the full runtime TCB layout or physical stack consumption.

Verification passes 32 lifecycle pairs and 528 worker pairs against raw stock. Cases cover failed queue/thread allocation through the actual common BASEPRI-64 fault primitive, stop-after-error/mutation, zero and full-word watchdog values, queue publication ordering, initializer ordering, notification boundary values, multiple iterations and watchdog replacement during arm/disarm/dispatch/feed. Each nonreturning run stops at the next notification wait after the selected input sequence. Provider callbacks clobber caller-saved registers; private frames and incidental registers are not compared.

Another 176 pairs execute the actual existing startup sync wait/signal code. The queue/thread and notification leaves, hardware initializers/dispatcher and watchdog providers are modeled. Hardware child entry ABIs, including any scratch/history assumptions, remain separate verification gates; these tests do not establish full child integration or physical charging/NFC operation.

Eight compiled defects are rejected: wrong queue capacity, publishing the queue too late, dispatching an invalid status, missing watchdog arm, caching a changing watchdog handle, skipping idle feed, clearing before termination and ignoring thread allocation failure. The final normal probe passes again after all mutants. REA windows bind the worker/literals, lifecycle entries/literals and attribute record to the locked stock application.

The audit preserves 805 prior object hashes, including the existing battery handle, sync implementation and common fault provider. There is one application definition of the battery thread-handle owner. Generated boot objects retain allocated bytes and normalized relocations. The manifest only adds the new unit. No source qualification plan or G2 source is changed.

The task cannot run to completion without the four explicit hardware dependencies, manager wiring, final application layout/linking and device validation. Probe scripts, results and hashes are in [nfc-charge-task-c-review.json](nfc-charge-task-c-review.json).
