# Standard memory APIs resolve BLE and formatting dependencies

`native_memory_api.c` supplies the standard `memcmp`, `strncpy` and `memchr` symbols required by the compiled Nordic BLE and formatting providers. Comparison and padded copy delegate to the existing reconstructed C routines in `native_libc_sequences.c`; no second comparison/copy algorithm is introduced. Byte search is a bounded unsigned-character loop with the standard integer-to-byte conversion.

The [receipt](memory-api-c-review.json) records 2,469 C API checks: 554 comparison, 681 padded-copy and 1,234 search cases. Comparison/copy cases also execute their locked stock routines; search uses an independent byte-search oracle. Cases cover zero length, NULL pointers at zero length, high bytes, positive/negative differences, differing positions, embedded NUL padding, length exhaustion, unaligned buffers and full-width search values. Exact mapped-end guards check that bounded search/comparison do not overread. Four defective variants with boolean comparison, shortened copy, wrong returned pointer or unconverted search integer are rejected.

The subset ELF links the new API unit and existing C algorithms without native bindings, stubs or unresolved symbols. Stock bytes are loaded separately only for comparison/copy oracle execution. REA raw-byte observations identify those stock entries. This establishes the memory API subset, not a full firmware link, physical BLE operation or stock `memchr` byte identity.

The normal report is `build/sources-goal-r1-memory-api-c/report.json`: 728 units compile without failures or duplicate strong symbols. Application imports fall from 178 to 175; bootloader imports remain 34. `memcmp` resolves Nordic advertising, authentication, GATT cache and identity-manager references; `memchr`/`strncpy` resolve formatting references. One unit was added, and all 727 previous objects are byte unchanged. Both manifests pass `make sources-check`. No source-plan selection was added.

The unresolved generic CMSIS `OS_Tick_GetCount`/`OS_Tick_GetInterval` calls remain separate work. Their consumer combines FreeRTOS ticks with a sub-tick interval and reports the CPU clock frequency, while the nRF port schedules from RTC. Mapping them directly to RTC counts without reconciling those units would invent timer behavior; this review does not provide such aliases.
