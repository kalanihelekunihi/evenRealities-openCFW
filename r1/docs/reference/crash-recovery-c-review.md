# Retained health crash recovery helpers in C

`runtime/native_crash_recovery.c` supplies stock clear `0x58914` (34 bytes), accessor `0x58980` (42 bytes), marker probe `0x58a24` (22 bytes) and CRC validator `0x5a28c` (40 bytes). REA instructions establish all four local bodies. The implementation reuses `r1_reset_trace_context` from `native_reset_retained.c`, the pinned C CRC16 routine and C memory clear. It adds no duplicate retained-memory owner, inline assembly or executable blob.

The clear snapshots active record context word 2, clears 900 bytes at record +12, computes CRC over exactly 964 bytes and stores its low halfword at +964. It returns the raw CRC result. The validator first checks the leading `0x5a5a5a5a` marker, then compares the same CRC extent to the saved halfword. The accessor rejects a null length pointer before validation, reloads the active context after validation, checks the blob marker at +908, stores length 896 and returns record +12. The marker probe publishes context word 1 to word 4 before dereferencing and testing that address, including on the fault path.

The producer's 736-byte payload advertisement remains distinct from the accessor's 896-byte admission. The clear covers those 896 bytes plus their four-byte marker, while retaining the trailing 52-byte snapshot before the CRC. No length was changed to make the recovery path succeed.

Production-object replay passes 1,740 stock/C pairs. It covers three leading marker values, blob-marker match/mismatch, valid/invalid CRC, zero/ones/random record patterns, all four record alignments, three interrupt-mask combinations, null and aliased length pointers, and six invalid-pointer fault pairs. It also checks null-output short-circuiting with a null active record. Complete retained/context/output/guard/caller bytes, raw R0, SP, caller-preserved registers and masks agree. This does not establish ordered clear writes, arbitrary MMIO aliases, full exception frames, concurrent changes or hardware persistence across a physical reset.

An additional 192 pairs execute the actual stock lifecycle initializer at `0x4bd98`, routing recovery calls through these C providers. Authorization failure/retry, initialization failure/-5 retry, raw mode values and marker/CRC combinations are exercised. The C marker probe executes 32 times and accessor 16 times. Authorization, previous/profile loading, timestamp, engine initialization, activation, subscription and logging flags are modeled; logging flags are zero. The 896/736 mismatch prevents the recovery-copy/clear path in these runs. This is integration evidence for the new helpers, not a complete C lifecycle implementation or proof of engine initialization.

Three compiled defects are rejected: clearing only 896 bytes, advertising the producer's 736-byte length, and using a 960-byte CRC extent. The direct subset links without undefined symbols, native-address bindings or placeholders, using actual source owners and lower C providers. It contains the four C roots as defined text.

The normal build passes 721 R1 units (647 application / 74 bootloader), with no failures or duplicate strong symbols and unchanged 177 application / 34 bootloader imports. Both source manifests pass. No source-plan selection, instruction identity, complete firmware closure, physical reset recovery, flashing, commit or publication is claimed.
