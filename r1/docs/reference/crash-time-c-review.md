# Retained crash-time recovery in C

`native_crash_recovery.c` now supplies time metadata clear at stock `0x58960` and time accessor at `0x589e8`. They share the existing `r1_reset_trace_context`, C CRC16 routine and record validator. No retained-memory owner, executable blob or assembly is added. Fresh REA raw-byte reads and locked Thumb disassembly establish both routines and their health-database startup caller at `0x70030`.

Clear snapshots context word 2, clears complete words at record +4 and +8, computes CRC over exactly 964 bytes and stores/returns the CRC at +964. It preserves every other record byte. The accessor rejects any null output before validation, checks the existing marker/CRC validator, reloads the active context, and rejects a zero timestamp. It then publishes timestamp, unsigned offset halfword and bit 0 of the pending flag in that order. Ordered volatile reads/stores preserve aliases where earlier output writes change later metadata reads. Failure leaves outputs unchanged.

The binding-free subset executes actual C validation, CRC and retained-context storage. All 1,230 direct stock/C pairs pass, covering marker/CRC validity, zero/full-width timestamps, flag bits, offset words, three record patterns, four alignments, interrupt masks, null guards and aliases among outputs, context and retained storage. Clear also passes an independent CRC calculation and exact preservation check. Four compiled defects confined to the new helpers are rejected: wrong CRC span, wrong pending bit, missing zero-timestamp guard and missing metadata clear.

A further 128 paired runs execute the actual stock database-startup body at `0x70030`, routing only retained helpers through C. The C marker probe executes 64 times, accessor 32 times and clear eight times. Cases vary initialization failure, retained validity/time/pending state, preexisting mutex and allocation failure. Time restoration, next-day range preparation, query/free and snapshot paths retain the same trace and record/context effects. FlashDB, mutex, subscription, time/calendar, allocation/query and snapshot providers are modeled, with log modes zero. This is integration proof for these helpers, not a C implementation of the startup body.

The normal report `build/sources-goal-r1-crash-time-c/report.json` compiles all 732 R1 units and composes both payloads without failures or duplicate strong symbols. Imports remain 156 application / 34 bootloader. All prior allocated code/data and named relocations are unchanged. Two new helper sections are added; a lifecycle log constant receives a compiler-generated section-label change with identical contents. The other 730 object hashes are unchanged. `make sources-check` passes.

The [startup dependency reference](health-db-startup-dependencies.md) records the remaining interfaces/layout requirements. Arbitrary faults/MMIO aliases, interrupt interleavings, physical reset persistence and a complete source firmware link remain unverified. Optional byte matching is not claimed.
