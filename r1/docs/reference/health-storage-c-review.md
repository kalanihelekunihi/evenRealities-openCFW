# FAL-backed health key and previous-state recovery in C

`native_health_storage.c` now supplies stock lazy FAL binding `0x6ba68` (146 bytes), key loading `0x6ad80` (282 bytes) and previous-state restoration `0x6afb0` (180 bytes). All three local REA instruction dossiers are retained with the probes. The new shared 12-byte owner matches native offsets at `0x20006ee0`; executing the locked scatter decoder confirms all twelve cold bytes are zero. No inline assembly, executable byte arrays or duplicate storage owner is added.

Binding looks up `pKey.bin`, stores the partition result and looks up its flash-device name at +28. Partition failure leaves the old driver word untouched. Driver failure clears the partition only after logging. Success sets the initialized byte to one; failure does not reset a preexisting initialized byte. Key loading binds only when that byte is zero, then checks partition/device availability before key/null-length policy.

The key metadata is an eight-byte header seeded from incoming R2/R3, not prefilled with erased bytes. Stored length must be 64, but the actual payload read and CRC use the caller's requested length. Flash-read return statuses are ignored as in stock. The native non-reflected Castagnoli CRC32 starts at zero. The loader returns status in low R0 and either original length or computed CRC in R1, represented by a standard C uint64 return.

Restoration aligns key/state lengths using wrapping 32-bit arithmetic, scans slots 3 through 0, and reloads partition/device state between reads. Its header is seeded from state pointer/length and persists across partial slot reads. Erased length `0xffffffff` is rejected even if requested as the state length. A matching header triggers the payload read regardless of its return status. The returned high word is original key length unless structured logging uses that saved slot for the record offset. The lifecycle caller now uses the shared typed header and explicitly tests only the low result word.

The direct production-object replay passes 812 pairs: 72 binder, 386 loader and 354 restore cases. There are 46 successful and 340 failed loader cases, plus 250 successful and 104 failed restore cases. Coverage includes partial metadata/payload writes, negative/full-word read statuses, changing log masks, retained seed bytes, late CRC-header updates, callback retargeting of partition/device pointers, reverse-slot selection, wraparound offsets/lengths and output aliasing with owner storage. Provider arguments, read sequence, header snapshots, complete caller-visible memory, raw R0/R1 for value-returning boundaries, SP, masks and caller-preserved registers agree. Private pointer locations are compared by contents rather than frame identity; binder return registers are excluded for its void contract.

An initially incorrect CRC polynomial in the fixture kept the slot scan unexercised. A surviving erased-length defect exposed that gap. The fixture now uses non-reflected Castagnoli and asserts both successful and failed loader/restore outcomes. The corrected 653-case lifecycle/event/reset replay records 400 key reads, 1,087 state-header reads and 171 state-payload restores. It executes the actual C storage and checksum routines; FAL lookup, flash and other lifecycle providers are modeled/native-bound. Physical flash operations, concurrency, invalid callbacks and full firmware integration remain unproven.

All four compiled defects are rejected: aborting on a negative read status, accepting erased length, rounding state lengths down, and treating the complete 64-bit restore result as Boolean. The last control verifies the coordinator's low-word cast when restore status is zero but saved R1 is nonzero.

The normal build passes 724 R1 units (650 application / 74 bootloader), without failures or duplicate strong symbols. Application imports fall from 180 to 179 by resolving the restore provider; bootloader imports remain 34. The existing coordinator object changes alongside the new storage unit; the other 722 objects remain byte unchanged. Three lifecycle engine providers remain unfinished: authorization setup, profile loading and engine initialization. Both manifests pass. No source-only storage/lifecycle link, source-plan selection, device deployment, commit or publication is claimed.
