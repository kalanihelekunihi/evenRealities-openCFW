# LZ4 v1.10.0 isolated source-candidate audit

Status: authenticated research candidate; not production-configured; no
firmware or package artifact changed.

## Outcome

`research/candidates/evenhub_lz4_1_10_0.c` preserves the four-argument
`open_cfw_lz4_decompress_safe` ABI and delegates directly to pristine upstream
`LZ4_decompress_safe`. The production `evenhub_lz4.c`, `overlay.json`, all
manifests, aggregate pins, and package artifacts remain untouched.

The direct upstream candidate is preferable to the current hand adaptation
for semantic fidelity: it has the official safe decoder's exact malformed
input behavior and parsing restrictions. It is **not**, however, proven more
stock-authentic than a direct reuse of official v1.9.4. Primary-source review
shows the recovered length-reader evidence is shared by v1.9.4 and v1.10.0, so
the stock point release remains unresolved.

## Point-release correction

The former recovery audit incorrectly called four helper properties
v1.10.0-only. Official
[`v1.9.4` `lib/lz4.c`](https://github.com/lz4/lz4/blob/v1.9.4/lib/lz4.c)
at commit `5ff839680134437dbf4678f3d0c7b371d84f4964`, tree
`939d919c3903b42ed637542a4799fb3f4fa8b5fc`, is 113,390 bytes with SHA-256
`b6a85fd8f9be0fedb568abd1338719b23b999583ccda6f3404d5ae11e4ce7b8e`
and Git blob `654bfdf32f96ac633a5d4bc4dde097dbdff46882`.

Its lines 1901–1928 already use:

- the three-argument `read_variable_length` signature;
- the `(size_t)-1` `rvl_error` sentinel;
- the strict post-increment `*ip > ilimit` bound; and
- the 32-bit `length > ((Rvl_t)-1/2)` guard.

v1.10.0 splits the first extension-byte iteration before the loop and adds a
fast return for a non-`255` byte. The edge semantics above are unchanged, and
an optimizing compiler can generate the split control flow from either source.
The test fixture executes both source forms with explicit 32-bit accumulators,
including the first byte above `INT32_MAX`; their status, accumulated value,
and consumed count agree. These paths authenticate LZ4 but do not identify its
point release.

## Differential semantics

The focused verifier compiles the candidate, an independent pristine v1.10.0
oracle, the current production adaptation, and explicit 32-bit length-reader
models. It covers 101 deterministic compressed valid blocks, literal and match
length extensions, truncations, offset failures, 4,096 deterministic malformed
blocks, guard bytes, the >`INT32_MAX` extension accumulator path, and exact
negative returns.

The candidate and pristine v1.10.0 agree byte-for-byte. Three concrete gaps in
the current 5,133-byte production source (SHA-256
`090e8b652a7e7500926ac039222d86179c0b56bed24a6d881b069dbaec24a83a`)
are now pinned:

1. `f0 00`, capacity 512: production returns `-3`; official v1.9.4 and
   v1.10.0 return `-2`. The public contract only promises a negative error, but
   production does not preserve upstream's encoded error position.
2. `10 41 01 00 50 5a 5a 5a 5a 5a`, capacity 10: production returns 10 and
   writes `AAAAAZZZZZ`; both pristine releases return `-2`. The hand decoder
   checks for five final literals but misses the upstream `MFLIMIT` rule that
   the last match must start at least 12 bytes before output end. This is a real
   accept/reject parity gap and makes correction a promotion priority.
3. `10 41 00 00 50 5a 5a 5a 5a 5a`, capacity 512: production returns `-5`
   because it explicitly rejects offset zero; pristine upstream returns 10.
   Offset zero is malformed by the block format, so the production behavior is
   stricter, but it is not exact upstream behavior.

The G2 application wrapper maps a negative decoder result to zero, so the
MFLIMIT probe produces stock wrapper result 0 while the current hand decoder
would report a successful length before that outer mapping.

## Target closure

The target proof uses Cortex-M55 Thumb, `-O2`, freestanding/no-builtin,
function/data sections, no unwind tables, ROPI, and disables the LLVM machine
outliner so the selected closure is explicit. The wrapper is a four-byte tail
branch to `LZ4_decompress_safe`. Per-profile deterministic identities are:

| Profile | Upstream object | Selected decoder section | Wrapper object / section |
|---|---|---|---|

| Linux clang 22.1.8 | 91,896 B; `d0ffa7f3368c63cb5a524b0df73e2c5e42d8a834694f1b8d3991286dd44dd82c` | `.text.LZ4_decompress_safe`; 1,690 B; `6d7e83dea96cf39e7ff5d65a1f66116ced40d3f952d2b2074913fd97fd0a916b` | 976 B; `644dc82189c7be0a1e1fa61afd97946cb6a4477e677ad54e4f2792551024bc31`; 4-B section `90a54a1f68a806a1795bd044856908235426b3c0f67be605fb94d3d5344a747f` |

Both selected decoder sections have only the same four relocation targets:

- `R_ARM_THM_CALL` to `__aeabi_memcpy`;
- `R_ARM_THM_CALL` to `__aeabi_memmove`; and
- local `inc32table` and `dec64table` references. Apple clang emits one
  `R_ARM_REL32` relocation per table; Linux clang 22 emits paired relocation
  types 49/50 per table.

The two memory calls must be resolved to authenticated runtime providers during
promotion; the tables must be carried as source-owned data. No compressor
section belongs to this reachable closure. Two builds per toolchain profile
are required to be byte-identical.

Both target profiles compile the upstream and wrapper objects twice and require
byte equality before inspecting the profile-specific function section and
relocation closure.

## Production-promotion delta

Promotion must be atomic and is intentionally deferred. It requires:

1. replace the production hand adaptation input with the candidate wrapper and
   pristine `third_party/lz4/lz4.c` decompression closure;
2. teach/pin the overlay relocation plan for `__aeabi_memcpy`,
   `__aeabi_memmove`, `inc32table`, and `dec64table`;
3. update `NOTICE.md`, `EVIDENCE.md`, overlay/manifest source authority, and all
   source-coverage prose without claiming a proven stock point release;
4. rebuild and pin Apple/Linux target sections, the overlay, package, flash
   plan, checksums, ownership accounting, and rollback map; and
5. retain the MFLIMIT, negative-position, offset-zero, valid-block, malformed,
   32-bit-overflow, and guard-byte regressions.

Until that tranche is completed, this candidate is not a firmware input and
does not alter a flashable artifact.
