# G2 Touch residual NOP-padding reconstruction

SPDX-License-Identifier: MIT

This is a narrow, additive follow-on to the Touch shipped-prefix ledger
(`g2-touch-software-readiness-ledger.md`) and its current exhaustive
classifier (`tools/manifests/g2-touch-final-physical-byte-buckets.tsv`,
generated by `tools/analyze_g2_touch_relocated_semantics.py`). It answers one
question precisely: of the 19,442-byte `typed_external_or_unsupported`
complement, which bytes can be *independently reconstructed* (not merely
pattern-matched) from first principles, and does an independent
reconstruction actually match the pinned stock content?

## Scope

Two rows in `g2-touch-final-physical-byte-buckets.tsv` were already flagged
`reconstructible semantics; stock authority unresolved`, but no
reconstruction had been performed:

| Bucket | Bytes | Claimed content |
|---|---:|---|
| `typed_code_residual_arch_nop_padding` | 8 | "all remaining halfwords equal Thumb NOP encoding 0xBF00" |
| `typed_code_residual_legacy_nop_padding` | 126 | "all remaining halfwords equal Thumb legacy NOP encoding 0x46C0" |

Both are scattered, non-contiguous halfwords left over after the relocated
CFG/dispatch/literal/typed-data closure in
`tools/analyze_g2_touch_relocated_semantics.py` (`residual_pairs` in
`analyze()`); this document does not re-derive their addresses, and treats
that analyzer's already-committed, reviewed `content_sha256` pins as the
authenticated oracle for the *content* at those addresses. What was missing
was proof that the content is actually reproducible from source rather than
merely pattern-matched against the stock blob.

## Reconstruction

`tools/verify_g2_touch_nop_padding_reconstruction.py` assembles the two
canonical Thumb instructions with the project's own ARMv6-M toolchain
(`/opt/homebrew/opt/llvm/bin/clang --target=armv6m-none-eabi -mcpu=cortex-m0plus
-mthumb`, the same toolchain used for `components/touch/source_image`):

- `nop` compiles to `00 bf` (little-endian 0xBF00, the ARMv6-M Thumb `NOP`
  hint instruction).
- `mov r8, r8` compiles to `c0 46` (little-endian 0x46C0, the pre-Thumb-2
  "legacy" NOP idiom of moving a high register to itself).

Each encoding is tiled to the pinned byte count (4 halfwords / 8 bytes for
the architectural NOP, 63 halfwords / 126 bytes for the legacy NOP) and
hashed. Both reconstructed SHA-256 digests are byte-for-byte identical to the
`content_sha256` values already pinned in
`g2-touch-final-physical-byte-buckets.tsv`:

- arch NOP padding: `0fbf3781a949ae1c40a167e8b22998fc9b6135f6d0135f97da55de21d94f0b01`
- legacy NOP padding: `ce9feda3cee7af78db19513116d9f98419f1fc6d421c618e5b56fecb26e16c0e`

This is a genuine reconstruction, not a copied byte array: the two-byte
sequences come from the compiler's own encoding of a standard instruction
mnemonic, and the verifier fails closed if the toolchain ever stops emitting
that exact encoding or if the pinned digest changes.

Reproduce with:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 tools/verify_g2_touch_nop_padding_reconstruction.py --json
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest tests.test_g2_touch_nop_padding_reconstruction
```

## What this does and does not close

- 134 of the 19,442 `typed_external_or_unsupported` bytes now have an
  independent, compiler-based reconstruction proof instead of an unverified
  "reconstructible semantics" note. `production_routed` stays `false` for
  all of it: the source-built Touch candidate
  (`components/touch/source_image`) is a freestanding link with its own
  layout, not an address-matched replacement of the stock image, so there is
  no buildable artifact to place these two specific halfword patterns into
  at their stock addresses without re-introducing an address-matched
  candidate (out of scope here; see `TC-001`/`touch-source-experimental` for
  that routing track).
- The classification buckets themselves (`g2-touch-final-physical-byte-buckets.tsv`,
  `source-coverage.md`, `progress.md` totals) are unchanged: no bytes moved
  from `typed_external_or_unsupported` to `project_source_candidate`, and the
  19,442-byte figure is still correct. This document and its verifier are an
  additional, narrower reconstruction proof layered on top of the existing
  pin, not a relabeling of the bucket.
- The remaining 19,308 bytes of the complement stay exactly as classified and
  are not addressed here:
  - `typed_code_capsense_cat2_mixed_provider` (7,000 B): Infineon
    CapSense/CAT2 mixed provider, EULA-or-Apache-2.0 boundary unresolved.
  - `typed_code_owner_unresolved` (6,686 B): expanded CFG/dispatch
    complement with no surviving concrete owner.
  - `typed_code_referenced_literal_data` (1,924 B): PC-relative literal
    pools tied to that unowned code.
  - `typed_code_residual_return_tail` (4 B) and
    `typed_code_residual_typed_data` (60 B): NOASSERTION, unresolved
    ownership.
  - `typed_code_residual_zero_halfword_alignment_or_data` (46 B): zero
    halfwords where alignment-versus-data is intentionally unresolved (a
    zero halfword is not a unique reconstruction target the way a NOP
    opcode is, since it is also valid arbitrary data).
  - `typed_noncode_vectors` (192 B): the ARMv6-M vector table; the source
    image's README already marks vector ownership evidence-locked pending
    hardware qualification.
  - `typed_noncode_strings` (1,640 B): retained EasyLogger/product text.
    Reproducing the literal text verbatim from the stock blob would be
    copying shipped bytes into source, not reconstructing them from an
    independent generator, so this is left as typed/retained, not
    source-authored.
  - `typed_noncode_config_and_tables` (1,756 B): resident configuration and
    tuning tables whose schema and ownership remain unresolved (Infineon
    CapSense/Em_EEPROM provider boundary).

No hardware operation of any kind was performed. This item has no bearing on
hardware qualification, which remains blocked by unavailable physical
evidence.
