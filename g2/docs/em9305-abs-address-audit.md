# em9305: hard-coded stock-address audit (wave 25)

Why: units converted from IAR-style asm to arc-gcc C can change size, so every later symbol moves. Anything that embeds a stock address as a literal then points at the wrong place.

## Method
1. Link the composed `g2-em9305.o` twice (`.waves/abs/link.sh`): once at the base layout (`base.ld`) and once with `. += 0x100` inserted before the code (`shift.ld`).
2. Disassemble both and compare. An instruction operand or literal word that is identical in both images but lies in the code or rodata range is a hard-coded address (`.waves/abs/hits.txt`, `insn-hits.txt`).
3. Aligned-word scans over the whole image were noisy (instruction fragments), so they were limited to symbol-start values and to the rodata range 0x335d78..0x3373c8.

## Caveat
The current image is already not at stock layout. Symbols embed the stock address in their names but do not sit at them (base image 217,036 B vs the 210,888 B stock code record). Hard-coded stock addresses are therefore already wrong in our build, independent of any conversion. Fixing them is a correctness improvement, not only a safety margin for later shifts.

## Fixed in wave 25
The four QP assert module-name strings (stock 0x33451c, 0x334520, 0x334538, 0x334540) were referenced as literals from `activate.c`, `scheduler.c`, `event_gc.c`, `queue_pool.c` and `controller_init.c`. They now live in `g2/src/em9305/qpc-scheduler/qp_module_names.c` (`opencfw_em9305_qp_module_qk`, `_qf_dyn`, `_qf_actq`, `_qf_mem`) and are referenced symbolically. The new file is in `sources.json`.

## Fixed in wave 26 (all tables, function pointers, HCI handlers, vector table)
Every stock-address literal found by wave 25 is now symbolic, and the audit found more once the code behind them was looked at:
- Vector table: the stock image starts with a 66-word interrupt vector table at 0x302400 (word 0 = ROM reset 0x1003d0, 29 entries = default ISR 0x30f170, ISRs 0x305b1c..0x3067b8, SWI0/SWI1 and 8 ROM entries). Our image had no table, and stock 0x30ed96 loads `int_vector_base` with the literal 0x302400. Now `stock_residual_data.c` defines `opencfw_em9305_vector_table` (66 words, 58 symbolic, 8 ROM literals) in `.vectors`; the linker script places it first and asserts it sits at the NVM base.
- Unported stock code: about 160 stock functions were referenced only by raw address (HCI vendor handlers, ISRs, the vendor-NVM closure, lctr decode, PML/RF helpers, the 0x3288b0/0x3292f4/0x329368/0x31afd4/0x332b70 callbacks). They are now lowered verbatim in `stock_residual_code.c` (5,673 instructions, 17.5 KB, symbols `opencfw_em9305_stock_<addr>`), generated by `.waves/lower.py` and `.waves/gen26.py`. All branch targets and code-range immediates are symbolic; ROM calls are absolute `jl`/`j` (a limm jump cannot carry a delay slot, so the slot instruction is moved before the jump).
- Tables: `em9305_hci_cmd_tables.c` handlers are symbolic (ROM 0x10xxxx handlers stay literal); `stock_data_tables.c` holds the 0x334b98 pointer table and the byte tables; `stock_residual_data.c` holds the 0x333e9a radio tables, 0x3342d8, the 0x334d0c lctr function-pointer table (43 entries) and the 0x3357e0 tail (INI record, with symbolic code pointers).
- `init_callback_status.c` read the RAM pointer tables at 0x3357a8 and 0x3357b4 by raw address; now symbolic.
- Linker: `opencfw_em9305_image_end` replaces the literal 0x335bc8 that NVM_InitCopy compares against zero.

## Result of the audit (base vs +0x100 shift)
`.waves/abs/audit.py` (instruction operands and in-range words of data symbols) finds, on `g2/build/g2c-w26b-em9305`:
- 6 instruction hits, all legitimate: `and ...,0x333300` x2 (masks), `0x300000` x3 (flash base, range checks), `mov_s r2,0x302400` (the symbolic vector table, which the linker pins at the NVM base in both layouts).
- 2 data-word hits, both coincidental u16 pairs in radio tables (0x32004b, 0x3100a6), not addresses.
So the audit is clean.

## Flags and limits
- The first HCI table was extended from 12 to 34 records (stock bytes 0x3340bc..0x334254 are 34 contiguous records); only the first 12 are registered (count 0x334950). No consumer of the other 22 was found.
- `opencfw_em9305_image_end` as the meaning of 0x335bc8 in NVM_InitCopy is a guess. `opencfw_em9305_timer_channels_334448` is named from its use.
- The closure lowered two over-wide stock regions (0x302664..0x30299c and 0x329574..0x329842, 1.5 KB) that also contain functions that are already ported; the extra copy is dead code.
- The real QEP/QF functions (0x310da0..0x311490) are still unported (our QHsm/QActive vtable members are stubs), a separate gap.
- Data is verified byte-for-byte against the stock record (raw tables) and word-by-word (pointers resolve to the expected symbol). Lowered code was checked by mnemonic sequence (5,673 vs 5,673; the only differences are `bl`->`jl` for ROM calls and branch-hint bits) and by operand multiset. The QEMU harness was not run on these units.

## Wave 27 re-run
After replacing the QEP/QF/QK stub and hand-written units with the unmodified QP/C 6.5.1 sources (`g2/src/em9305/qpc-port/`), `.waves/abs/link.sh` + `audit.py` on `g2/build/g2c-w27-em9305` give the same result as above: 6 instruction masks/flash-base hits, 2 coincidental data words. The QP globals are linker-pinned (`QF_active_` 0x80131c, `QF_maxPool_` 0x801360, `QF_pool_` 0x801368, `QK_attr_` 0x801394), the vtables are symbolic (no stock address), and the hand-written stock bodies `QF_init`/`QF_run` still write the pinned SRAM addresses absolutely (pins are in the link script, so these are layout-safe).
