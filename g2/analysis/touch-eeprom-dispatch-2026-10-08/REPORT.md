# EEPROM write-direction correction and dispatch

The historical `Cy_Em_EEPROM_Read` label at0x8aac is wrong for the inspected locked image: its selected simple-mode body0x85d4 copies application input into a RAM row buffer and calls a row-program helper. The analogous extended body0x8808 assembles row sequence/header/checksum and copies application input into its payload. The public Infineon candidate at release-v2.20.0 pin `0eeaba0dd7364dfa6badb48fe5d6692309a949e5` identifies this family as `Cy_Em_EEPROM_Write`, `WriteSimpleMode`, `WriteExtendedMode`. This is behavioral attribution, not an exact producing-version or compiled-byte claim. The separate0x8a78 dispatcher calls the read family. Shared historical catalogues and accepted evidence remain untouched.

`write_dispatch.c` independently reconstructs the48-byte dispatcher: reject size0; reject modulo32(address+size)>context capacityu32+8; reject null data; select simple provider when context byte13 is nonzero, extended otherwise; pass through provider status. Rejection is093e0000. Valid context is a precondition. Raw addition overflow is preserved as evidence, not recommended input handling for new applications. Provider bodies remain explicit guarded assembly test boundaries, not implemented storage operations.

Final standalone ELF `15308e4a0ae862ef617a073a9fcd929ed922759fa85cd37740c59ab94b0c62de` passes **2,304** original/source comparisons of returns, provider choice/arguments, unchanged RAM/context, SP and PRIMASK. Two mode/overflow mutants are rejected. Initial C boundary bodies were optimized away by Clang, so the fixture was corrected to separate external assembly symbols that trap unless intercepted; only the corrected run is accepted. No provider instructions execute in these dispatch comparisons.

`verify_simple_direction.py` additionally executes the **actual stock simple-mode, division and memcpy instructions in96 cases**, with row-read callback and row-program helper0x8554 explicitly cut to synthetic RAM/status behavior. It proves input bytes flow into row scratch20000cd4, preserves other row bytes, leaves input unchanged, advances last-written-row only after success, and stops at injected row failure. It is original-body behavior evidence, **not native-source equivalence** for the168-byte provider. Row-size16/32 and guest RAM flash are fixture choices, not stock flash geometry claims.

Application0x3a38 first sets UNVE sentinel then supplies8 config bytes through0x3568 into this write family. Command7's deferred flag therefore requests persistence rather than reloading old config. Its immediate ACK precedes that operation and cannot report its later result. Hardware programming/durability is unverified. The124-byte lower row helper0x8554 and downstream0x7ea4 provider-vtable operations remain unexecuted boundaries; actual context geometry/provider functions require further analysis. Public source was inspected under its bundled EULA in a temporary checkout; only provenance/hash and independent reconstruction are exported here.

Next actionable leads are provider vtable slots and row-program error handling, followed by extended-mode historic-row/checksum behavior. This batch does not exhaust EEPROM source or prove firmware persistence. No actual flash, index or accepted checkpoint changes occurred.
