# Intermediate CMDQ curIdx ownership remains unclosed

Stock `update_indices` at0x538d18 can store an intermediate wrapped index and then the corrected index to RAM `queue+0x1c` while PRIMASK is1. The existing optimized C provider stores only the corrected value in this case. Prior release evidence retains and asserts each raw sequence, then narrowly normalizes that contiguous masked helper sequence for its synchronous contract comparison. No new source change or volatile qualification is made here; power-preparation sequence cases use a nonwrapping index and do not close that contract.

There is concrete evidence distinguishing the RAM slot from the hardware register: the descriptor at queue+0x24 has `regCurIdx` at descriptor+8. Authenticated IOM rows at0x6c0f40 point that field to `0x40050000 + (module<<12) +0x240`, not queue+0x1c. Stock post-block instructions538fe6..538ff0 load that descriptor register address, OR the requested interrupt bit into it, and emit an address/value command pair. The pinned upstream `am_hal_cmdq_post_block` has the same role. That particular queue command therefore targets the hardware index register.

Stock status consumer53901a calls update_indices at539040, then reads queue+0x1c at539044 and copies it to the caller's status. It observes the final value on this serialized call path. These bodies and addresses are preserved in original-disassembly.txt.

Neither observation is a closed-world actor audit. We have not excluded NMI, another CPU, arbitrary DMA descriptors, or another caller reading RAM queue+0x1c during the masked sequence. PRIMASK alone does not establish their exclusion. To promote asynchronous compatibility, obtain a verified actor/call-graph and DMA-address reachability proof for this slot, or an appropriately instrumented authoritative runtime trace and the relevant platform memory/interrupt contract. The present evidence only narrows the exposed hardware-command target; it does not prove the optimized intermediate-store difference harmless on hardware.
