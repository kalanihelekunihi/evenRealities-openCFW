# Independent review: FreeRTOS Event Group WSF provider

Static and bounded verifier review. The fresh result is `g2/build/foundation/event-group-wsf-simulator/comparison-first.json`: PASS, 218 cases, 1,222 unique original instruction bytes, ELF SHA-256 `c32cb39e389f1bce6a96f84ddb92c80309cf7a629eed87586c189e6addb2b622`, authenticated firmware SHA-256 `36c5b0e499a68ac2493a497bdab9740fd3e7027730c26a9094eca47268a27863`. Its manifest binds the current event-group sources, linker script, and verifier hash. This supports the bounded source-vs-stock behavior comparisons described below; it is not whole-kernel or scheduler equivalence.

The four extracted function bodies in `components/foundation/freertos_event_group/event_groups_subset.c` and `timer_pend_subset.c` match the corresponding cached upstream bodies byte-for-byte as text. The provenance file identifies FreeRTOS Kernel V10.5.1, commit `def7d2df2b0506d3d249334974f51e427c17a41c`, and retains the MIT notice. It claims API-function reuse, not a complete kernel build. Compatibility static assertions encode a 32-bit `EventGroup_t` with its wait list at offset 4, a 20-byte list and a 16-byte timer daemon callback message. This appears structurally consistent with the declared 32-bit sparse ABI, but still depends on the firmware's exact trace/allocation configuration and associated structure layout.

The task-context body has the expected event-group behavior: it ORs only low event bits, captures `pxNext` before an unblock can move the current waiter, accumulates the union of matching clear-on-exit masks, clears after the full traversal, resumes the scheduler, and returns the final event-bit word. That return value is not an operation-success flag. The ISR wrapper packages callback, group handle and bits into the timer-daemon command; `xTimerPendFunctionCallFromISR` passes its stack-local 16-byte message to the queue boundary, which must copy it synchronously before returning.

One boundary needs explicit treatment in any result claim: upstream `xEventGroupSetBitsFromISR` does not assert the handle or reserved high bits. It returns the timer-queue send result. An invalid handle or forbidden bits reach the fatal `configASSERT` only later if the deferred callback executes `xEventGroupSetBits`. A test that enqueues such a command cannot describe it as an immediate ISR assertion or an enqueue failure. The diagnostic provider is terminal and is not an error-return behavior.

The adapter maps the WSF handle argument to `EventGroupHandle_t`, and the linked verifier runs both stock WSF callers and the bounded event-group APIs. The corrected timer queue pointer is `0x20074ab0` (the firmware load at `0x47eb6c`); the compatibility header and harness both use that address. The comparison exercises actual original setter, ISR wrapper, timer-pend wrapper and callback instructions, plus linked WSF/radio/GPIO code. It passes 218 cases including matching modes, clear-on-exit unions, repeated sets, waiter unlink mutation, task return values, ISR queue status/higher-priority output, and task/deferred invalid-argument diagnostics. The verifier checks source and stock results/state/calls/writes and an independent task-context event-bit model.

The unlink fixture removes the matched item, decrements the list count and overwrites that item’s `pxNext`; successful multi-waiter traces therefore exercise the saved-next path. ISR cases inspect the 16-byte command at the queue-call boundary and the fixture snapshots it when the send succeeds, then poisons the source stack bytes before any explicit daemon delivery. Queue-full and successful sends are both covered. Manual callback delivery, queue-copy timing, scheduler suspend/resume, list unlink, context/tick/wait, and application handlers remain fixtures shared by stock and source runs. This does not establish the production timer daemon’s scheduling, actual kernel queue capacity/copy implementation, or task readiness. The invalid-ISR cases correctly show no assertion at enqueue; a later explicit delivery reaches an invalid-argument path.

Correction: earlier wording called the invalid-case stop a terminal diagnostic entry. The stock path is actually intercepted at `0x5fa0a4`, the BASEPRI mask-helper entry shared by this failure branch. The verifier stops before that helper executes and before the following fault store/endless loop; source-side invalid cases stop at the diagnostic provider entry. Thus these cases establish only that the bad-argument branch reaches its respective interception point. They do not demonstrate equivalent assertion completion or a full fatal path. Valid-input comparisons are unaffected.

No concrete correctness blocker was found in the bounded valid-path review. Remaining scope limits: no real scheduler or queue implementation, no event-group lifetime/destruction or concurrent use proof, no full fatal-assert path, and no physical ISR behavior. The comparison is source-semantic correspondence, not a claim that the reconstructed module’s compiled bytes match the firmware.
