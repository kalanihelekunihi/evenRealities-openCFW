# Independent review: Ambiq GPIO pin configuration

**Result: bounded review passed; no implementation blocker found.** The selected stock functions are the pin configuration getter at `[0x480EEE, 0x480F0C)` (30 bytes) and setter at `[0x480F0C, 0x480F8A)` (126 bytes). The addresses and code bounds are consistent across the authenticated payload slices, the disassembly, and the new verifier. Their selected source bodies match the pinned Ambiq SDK 5.1.0 excerpts recorded in `SOURCE_PROVENANCE.json`; this supports reuse of these two bodies, not whole-driver or byte-identical firmware claims.

The public SDK body checks the 224-entry logical pin range before accesses, checks getter output for null after range validation, uses the two seven-word capability maps for setter validation, and protects the successful key/config/lock writes with saved PRIMASK. The compatibility view places the 224 volatile 32-bit configuration cells at GPIO base `0x40010000` and PADKEY at offset `0x400`, matching the stock register pointers and accesses. The value-passed `am_hal_gpio_pincfg_t` is four bytes and is read/written as the complete raw word. Its bitfield layout is target-compiler ABI-specific; the tested Cortex-M Thumb profile and by-value call convention are consistent with the stock call sites, but this is not a portable host ABI.

The verifier is meaningfully bounded and well checked: it compares the locked `36c5b0e4…` firmware against the source ELF, checks both table contents against authenticated stock data, confirms fetched code bytes, checks the independently modeled status/results and complete logical-register state, and records ordered MMIO accesses, caller output writes, and PRIMASK during writes. I independently replayed 24 selected vectors with the same hooks using the installed Unicorn 2.1.4 environment. All matched stock, source, and the model. They include boundary/null getter cases, pin 103, normal-drive allow/reject cases, extended-pad pull 0/1/6/reject cases, both incoming PRIMASK values, and the actual raw radio/display constants. The rerun covers 160 unique original instruction bytes in this selected set; the campaign's separate `comparison-reviewed.json` reports 9,304 cases and all 156 declared getter/setter bytes executed, plus the already-accounted eight-byte PRIMASK helper.

The tests support a register-level contract, not physical behavior. The emulator supplies ordinary raw MMIO state and does not model pad electrical behavior, key-lock enforcement, pin mux routing, peripheral clocks, or board power timing. The accepted configuration values therefore should not be presented as a physical pin capability certification. The upstream expression `1 << (pin % 32)` is retained unchanged; the target compiler's behavior is covered by the ARM test vectors, while generic C portability or other compiler behavior is outside this evidence.

Static consumer evidence identifies concrete integrations without claiming caller execution. Radio shutdown caller `0x4B49CE` reaches helper `0x52DD7C`, which calls the setter for pin 138 with raw word `0x3`; its separate pin-93 output-state write remains outside this component. The display helper at `0x592C78` calls for pins 143, 128, and 142 using raw word `0x183`; its semantic label is explicitly inferred, and complete display power wrappers were not executed. Flash-associated function `0x46FB0C` calls the getter at `0x46FD10` for pin 103; its driver association remains unverified. These callers and their board sequences contribute no new execution coverage here.

No code or shared campaign state was changed during this review. The result and evidence file bind the exact firmware, ELF, and verifier hashes used for my representative rerun.
