## Exact token lineage

SDK sec_aes.c and sec_aes_rev.c use a shared uint8_t secCb.token: return old value and increment modulo256; if old value is FF, return the next old value and increment again. SEC_TOKEN_INVALID=FF. Thus old FE yields returned FE/new counterFF; oldFF yields returned0/new counter1; old0 yields returned0/new counter1. Successful AES-only generation cycles through0..FE with255 distinct tokens. This is identity reuse after wrap, not a generation number. Allocation failure returnsFF before increment/enqueue. Source CMAC/CCM paths also increment the shared byte counter directly, so the255-request period applies to the isolated successful AES/AES_REV sequence only.

## Connection lifecycle and fixture admissibility

SMP lookup indexes the connection slot by valid nonzero message param regardless of current slot connId. Source close callback sends SMP_MSG_DM_CONN_CLOSE to the state machine first, then clears connId; only its queued SMP transmit packet is freed. It neither resets CCB token nor drains aesEncQueue. Stock smpDmConnCback537502..5375C8 confirms close event40, dispatch at5375AC, clearCCB+61 at5375B2, optional packet free at5375BE, and no token+65 store. Open event39 initializes connection/state fields but also does not reset token+65. A late queued AES message after closure can therefore reach the handler with valid param1 and closed slot0. Whether reopening before delivery is scheduled in actual product operation is not established.
