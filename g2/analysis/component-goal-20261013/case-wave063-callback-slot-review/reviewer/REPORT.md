# Independent callback-slot review (wave 063)

## Result

Two source-level indirect-call type mismatches are confirmed within the reviewed CASE source inventory. Both can be repaired at the call sites by using the stored target's actual callable type, without changing the callback implementation or native argument/return behavior. This is a bounded available-evidence review; it is not physical hardware acceptance, a global firmware admission, or proof of callback lifetime/concurrency behavior.

## Findings

1. **DMA abort slot `dma + 0x38`: incompatible parameter type.** In `g2/components/case/source_candidate_20261010/dma_abort_provider.c:53-54`, `case_dma_abort_it` loads the slot as `void (*)(void *)` and calls it with `dma`. The only source registration found for this slot is `g2/components/case/source_candidate_20261010/uart_irq_continuations.c:30`, which stores `case_uart_dma_abort_callback`; that definition at line 15 has type `void(uint8_t *)`. Its fallback direct call at line 32 uses the `uint8_t *` type as well. Under C, calling the target through the incompatible `void(void *)` type has undefined behavior even though both argument values use the same pointer representation on this target. The locked image corroborates the call shape: at native PC `0x0800494a` it loads `[R0 + 0x38]` into R1, and at `0x08004950` it executes `BLX R1` without changing R0, so the callback receives the DMA pointer. The low-risk source correction is to type the loaded callback as `void (*)(uint8_t *)`; leave the separate RxISR slot and type alone.

2. **Sensor cancellation slot `p + 56`: incompatible return type.** `g2/components/case/startup_candidate_20261011/application_boot_sensor_cancel_callback_candidate.c:9-15` defines `case_boot_sensor_cancel_callback` as `uint32_t(uint32_t)`. `application_boot_sensor_irq_5f50_candidate.c:53` installs it in the slot, but line 55 invokes it through the generic `invoke` helper declared at lines 20-21 as `void(uint32_t)`. `application_boot_sensor_irq_restart_candidate.c:42` uses the same void-typed helper for the slot. A function type with `uint32_t` result is incompatible with one returning `void`, so these calls also have undefined behavior in C. The native cancellation call target at `0x080086e0` returns with R0 carrying the loaded state pointer in this path; the surrounding native callers discard the callback result. Use a cancellation-specific `uint32_t (*)(uint32_t)` call type and explicitly discard the result where appropriate. Keep the generic `void(uint32_t)` helper for genuinely void callback slots such as descriptor offset +116.

The two suggested corrections are call-site typing changes only. Do not change native parameter values or the callback's `uint32_t` return type to silence the mismatch: preserving the target's return register and discarding it at the callers matches the observed flow.

## Native branch negative control: no fallback argument finding

The high sensor fallback at native `0x0800604c..0x0800606e` does **not** take the `MOV R0,R4` at `0x0800606c`. The halfword at `0x08006050` is `0xe00d`; Thumb unconditional branch target is `(0x6050 + 4) + (0x00d * 2) = 0x606e`. Thus it jumps over `0x606c` directly to the `BLX R1` at `0x0800606e`, leaving R0 as the p value loaded at `0x0800604c`. The source fallback passes `rd(state)` (p) at `application_boot_sensor_irq_5f50_candidate.c:55`; that argument agrees. A review that reasons only from the shared `BLX` or merges its predecessors would incorrectly import R0 from the other branch. This is a checked negative control, not a third defect.

- The locked payload reviewed was `g2/blobs/official/g2-2.2.6.10/firmware_box.bin`, SHA-256 `36ca0c13558f252af286ae2b36b5e576d087d21d37b15d778e7da9f502a70374`. - Source inventory was checked by searching the CASE `.c`/`.h` tree for slot expressions, callback symbols, and declarations. For DMA +0x38, the source search found the consumer in `dma_abort_provider.c` and the setter/direct fallback in `uart_irq_continuations.c`. This is an inventory of this source tree, not proof that no external/assembly writer exists.

- This review did not run a firmware emulator or hardware. It does not verify callback ownership, lifetime, IRQ behavior, timing, or all behavioral semantics.
