## O1 discrepancy investigated, not closed

Reproduced exact requested=recorded8 failure: original read argument addressABC400 versus source key20020000. Disassembly shows unconditional LDR r1,[SP+84] at100076, and trace confirms that memory containsABC400. Source execution skips that LDR after an ITcc with false condition; observed xPSR IT bits remain nonzero at100074. Source r1 remains key. This is a concrete execution anomaly; it is not evidence that compiled source intentionally loads the key.

Limiting hooks to provider boundaries and explicit Cortex-M4 CPU selection both reproduce the failure. Two provider-free reductions of the exact instruction slices (ITcc alone; preceding ITT plus ITcc) execute correctly for request3/8/12. Therefore stale IT-state observation localizes the failed execution but does not yet isolate root cause; full execution/hook/translation context remains required. Files O1-failure.txt,O1-trace.txt,O1-ranged-log.txt,O1-m4-log.txt and minimal-IT*-results.json preserve positive/negative evidence. No candidate patch, instruction substitution or false O1 equivalence claim was used.

## Closure assessment

Cache64/64, name64, enum representation and write-granularity1 candidate constraints now have independent evidence. Selected O0 get/blob/header contracts are closed under mocks, with original low-byte correction independently confirmed. The broader FlashDB goal cannot close: whole find_kv/status/read/write/FAL implementation, init/create logic, read data, logging completion, real locks/concurrency, physical flash delivery, compiler/link identity and byte equality remain unverified. Prior bounded source-interface leads may be marked complete without upgrading this to complete dependency coverage. Remaining finite static provider implementations and O1 execution context are useful; physical delivery is a separate runtime boundary.

All five original extent receipts match the36c5 header-bearing official main payload. That artifact should not be described as stripped raw main, although all address mappings are correct. Source bodies get_kv/fdb_kv_get_blob/write_kv_hdr are unchanged; supplied macros/declarations/diagnostic/provider seams and wrappers prevent treating candidate.c as the entire public translation unit.
