## Concrete documentation contradictions and stale boundaries

1. docs/nema-gpu-model.md says GPU is opt-in and default still retained-register bank; current platform binds G2NemaGpu at40090000 and README calls it normal core. That historical text is stale for current source. Fragment opt-in remains meaningful.
2. Early Nema research's absent ISA reference is superseded by supplied RM-A5-1p1 TRM SHA5c98d47b00bff3b570bd2d938c46756bb1dc2bfdb806cfae91dbda2c83acb2af, pp348–355. src/g2emu/nema_isa.py is intentionally partial, fully_decoded alwaysfalse; conflicting opcode prose/extension/packing questions survive.
3. OpenCFW docs/tooling.md points to ~/Repo/g2-firmware-emulator while requested checkout is ~/Repo/jimrandomh/g2-firmware-emulator. Path existence/checkout equivalence cannot be assumed.
4. OpenCFW historical consolidated library citations refer to several removed g2/docs/research and g2/third_party paths. Their table may carry correct historical conclusions, but missing source paths are not current independently inspectable receipts. No canonical documents were changed.

## Highest-value finite validation steps

Freeze exact selected firmware/model/launcher hashes before each comparison. Audit the current pinned native Renode core'sMVE/low-overhead/FPU/exception instructions against bounded manufacturer vectors actually used by locked firmware; merely namingM55 is insufficient. Compare platform addresses/masks/reset/IRQ fields with Apollo510B SVD/TRM, prioritizing retained/constant-ready banks and inheritedApollo4 security. Trace2.2.6.10 bus-descriptor constants for ALS/nPM1300 and compare newer-image routing. For any claimed boot fidelity, require actual secure-boot/ROM/bootloader execution evidence rather than application entry. GPU/IMU/ARC gaps need their specific missing ISA/provider contracts; no generic model pass substitutes. These are proposed bounded validations, not launched jobs.

Confidence high for source-visible setup/limitations and nominal geometry; medium for transferred behavioral contracts; no independent physical-fidelity qualification. The overall answer is partial hardware representation suited to selected firmware paths, with substantial explicit substitutes and gaps.
