# Apollo G2 scheduler suspend/resume evidence

This packet authenticates the locked Apollo image bodies for `vTaskSuspendAll` (`0x454d7c`) and `xTaskResumeAll` (`0x454dcc`), with the directly-called tick helper (`0x45504c`), next-unblock-time refresh (`0x455876`), critical-section helpers, and the PendSV request helper. The executable evidence is `verify.py`, `results.json`, and `disassembly.txt`. Run with `~/.local/share/opencfw/venv/bin/python verify.py` from this directory. The script checks the OTA and decoded-image SHA256s, Ghidra body bounds and hashes, literal loads, and the pinned source blob before writing its outputs.

## Authenticated control flow

`vTaskSuspendAll` is a 12-byte Thumb body, SHA256 `3651c872be8fd55503df57fb49f5d0b7b94b0e784237141389a4b965b8edb6e2`. It increments the word at `0x20074a58` and returns. There is no critical-section or interrupt-mask call in this body. This matches the nested-suspension contract in pinned `tasks.c` lines 2090–2107; the body does not itself stop interrupts.

`xTaskResumeAll` is 306 bytes, SHA256 `548e05e1f8a2f498372dd1f4eb7c6536e093dbbfdb82fbe8f9b54231cedc8a09`. A zero suspension count follows the assert-failure path (assert helper then an invalid-address store/loop); normal behavior assumes a matching prior suspend. It enters the critical helper at `0x4420d0`, decrements the count, and only performs the pending work when the resulting count is zero. At the outermost resume it walks `xPendingReadyList` (`0x20073d24`), unlinks each task's event item at TCB+`0x18` and state item at TCB+`0x04`, then inserts the state item in the priority-indexed ready-list array at `0x2006a49c` (20-byte list slots). The priority is at TCB+`0x2c`; the body raises `xYieldPending` (`0x20074a44`) when the readied task's priority is greater than or equal to the current TCB priority. If any pending task moved, it calls `0x455876` to recalculate the next unblock time.

It then snapshots `xPendedTicks` (`0x20074a40`) and calls `0x45504c` once for each pending tick, setting `xYieldPending` if the tick helper returns nonzero, then clears the pended-tick word. If yield is pending, it sets its return value and calls `0x4420bc`, whose authenticated 18-byte body writes `0x10000000` to SCB ICSR (`0xe000ed04`) and executes DSB/ISB: this requests PendSV. Finally it exits the critical section through `0x4420e8` and returns the flag. This packet establishes the PendSV request, not execution of the exception handler or a completed task context switch.

The raw tick helper `0x45504c` is 338 bytes, SHA256 `438ad4e9e1a7b439671463b2bbfd13616ebb6de32bd2aad53b802d31f11cc050`, and has a direct call from `xTaskResumeAll`. It tests the scheduler-suspended count at `0x20074a58`; if nonzero it increments `xPendedTicks` and returns without advancing the tick count. In the resume path the count was just decremented to zero, so the helper's normal branch increments `xTickCount` at `0x20074a34`. It handles tick wrap through delayed-list switching, expires due delayed tasks and places them on ready lists, and returns a switch-needed flag based on the unblocked task priority, equal-priority time slicing, and `xYieldPending`. It calls `0x455876` on tick wrap and can invoke assert helper `0x5fa0a4` on the detected invalid list condition. The body and source support these facts; this packet does not claim a particular application tick frequency or that the tick helper was dynamically executed.

`0x455876` refreshes `xNextTaskUnblockTime` (`0x20074a50`) from the head of the current delayed list through the pointer cell at `0x20074a24`; when the list is empty it stores `0xffffffff` (`portMAX_DELAY`). `0x4420d0`/`0x4420e8` bracket the resume operation with a nested critical count at `0x2000309c` and BASEPRI mask helpers. The final yield helper is a PendSV-set write only.

## State and source evidence

The resume body resolves the following RAM globals through authenticated PC-relative literal words: suspension nesting `0x20074a58`; task count `0x20074a30`; current-TCB pointer cell `0x20074a20`; top ready priority `0x20074a38`; ready-list array `0x2006a49c`; pending-ready list `0x20073d24`; yield-pending `0x20074a44`; and pended ticks `0x20074a40`. Tick helper literals additionally identify tick count `0x20074a34`, current delayed-list pointer cell `0x20074a24`, overflow delayed-list pointer cell `0x20074a28`, and next unblock time `0x20074a50`. The script checks each literal address and value; the disassembly retains the instructions and body hashes.

The pinned FreeRTOS Kernel source is in `g2/build/foundation/freertos-upstream/tasks.c`, upstream tree commit `def7d2df2b0506d3d249334974f51e427c17a41c` (MIT). Its `tasks.c` Git blob SHA1 is `d97085d8736905c1eeb9d9e871c81e5970ee70ed`; file SHA256 is `14020d617b96dd2814e1211f6e3b645bcf5e2bd3179c23fe7dd16bc666fe9463`. Relevant source sections: `vTaskSuspendAll` lines 2090–2107; `xTaskResumeAll` lines 2174–2267; `xTaskIncrementTick` lines 2720–2898; `prvResetNextTaskUnblockTime` lines 3999–4024. The firmware's direct-call graph has 11 direct callers of each suspend/resume function; the exact caller addresses are listed in `results.json`. Among them, task/event/queue/timer helpers and memory allocation/free pair the calls; those addresses alone do not establish runtime execution.

## Limits

This is static binary/source correspondence only. It does not prove a full FreeRTOS configuration, execute the helpers, or establish runtime scheduler history. The assert-failure branches, PendSV handler, register/context save and restore, and actual task handoff remain outside the evidence. No firmware, source, shared interface, or build files were changed.
