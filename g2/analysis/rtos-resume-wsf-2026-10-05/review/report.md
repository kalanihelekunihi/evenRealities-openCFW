# Independent review: bounded FreeRTOS resume path

Reviewed the final resume verifier, linked target, pinned source identities, and `comparison-final.json`. I found no blocking issue in the bounded implementation or evidence.

The copied `vTaskSuspendAll`, `xTaskResumeAll`, and `prvResetNextTaskUnblockTime` bodies match the pinned FreeRTOS V10.5.1 source at commit `def7d2df2b0506d3d249334974f51e427c17a41c`; the focused test hashes their raw CRLF-preserving text and checks the MIT notice. The recovered pended-tick cell is `0x20074a40`. The linked target reuses the task critical provider and links a bounded PendSV request implementation. The request writes the PendSV-set value and executes DSB/ISB; it does not run a context switch.

The final result reports 267 cases and 2,106 unique original instruction bytes. Its firmware SHA, ELF SHA, and all six current component-source hashes match the files on disk. The verifier compares stock and source state, and independently models suspend nesting, pending-ready list draining, ready-list membership/order, task count, pended-tick replay count/clear behavior, yield state, next-unblock state, and returns. I ran `python3 -m unittest g2.tests.test_freertos_resume`; all three focused provenance, original-byte, linked-provider, and optimized-verifier checks passed.

The evidence boundary is appropriately explicit: `xTaskIncrementTick` is intercepted as a synthetic return-value provider. The harness checks how many times it is called, how its supplied results affect yield bookkeeping, and that `xPendedTicks` is cleared; it does not claim tick advancement, timeout expiry, or resulting delayed-task transitions. The PendSV request executes, but the context switch does not. Task/list/global state is synthetic, as are the remaining EventGroup unblock, scheduler-state/context/wait/tick callbacks, and application providers. The translation-cache workaround is applied symmetrically to stock and source and documented without claiming a general Unicorn root cause.
