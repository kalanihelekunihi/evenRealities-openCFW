# Initialized thread teardown callbacks

The locked DATA installer contains DFU teardown pointer `0x42dddb` at SRAM `0x200004d0` and manager teardown pointer `0x42e3cb` at `0x200004f8`. Their handles are at `0x200004d4` and `0x200004fc` respectively. Both wrappers read the handle; if nonzero, reread it, call the external target `0x416200` (named thread termination by the existing DFU C contract), then clear the stored handle regardless of the termination return value. If already zero, they skip the call. Both leave R0 zero. The clear follows the call; it does not prove the thread stopped or released other objects.

Existing DFU source `g2/components/bootloader/dfu_task/context.c` already implements its wrapper; this batch retains that implementation and supplies `teardown.c` for the manager wrapper. The fixed4b image has not been modified or promoted.

`comparison.json` contains48 original-instruction differential fixtures: both wrappers, zero/nonzero/high handles, three synthetic termination return values, and optional mutation of the stored handle by the controlled call. Both wrappers clear after the call even if its return is failure or it changes the handle.24/24 DFU and22/22 manager body bytes are visited; callee-saved R4, SP and PRIMASK match. Body/image/addon hashes are recorded. `external_boundary.S` is an explicit test veneer to the controlled termination service, not a scheduler implementation.

Relocation requirement: retain the DFU wrapper against linker garbage collection, link the manager wrapper and its actual external-call provider, and replace both DATA function fields with compiler relocations in a separate successor. Pointer retirement alone cannot establish teardown lifetime, IRQ cancellation, queue drain or safe destruction; those require actual termination-service and scheduler analysis. No hardware behavior or byte-identical claim.
