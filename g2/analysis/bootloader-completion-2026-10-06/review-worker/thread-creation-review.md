# Thread creation review

Reviewed the current sources in `g2/components/bootloader/thread_creation/` against the locked bootloader blob at load address `0x410000`. The blob hash is `f89a4c4657537cec6bfc572bdb8318866309b90a5d180c4307680d39824167b5`. I inspected Capstone disassembly and Ghidra exports for `0x41602A`, `0x416058`, `0x4160B0`, `0x4160FE`, `0x417C7C`, `0x417D94`, `0x41B46E`, `0x417E58`, `0x418A44`, and `0x41B2F8`/`0x41B30E`.

The normal static path source is consistent with the examined stock operations:

- Wrapper `0x4160FE` defaults to priority 24 and 256 words, rejects priority 0 or `>= 57`, rejects the low flag bit at attribute offset 4, converts the stack size at offset 20 from bytes to words, and takes the static route when the CB/size/stack fields qualify. Source behavior is at `thread_creation.c:15-32`.
- Static creation clears the 112-byte control block, writes stack pointer at `+0x30`, writes byte `2` at `+0x6D`, and delegates initialization. The initializer fills `words * 4` bytes with `0xA5`, computes `(stack + bytes - 4) & ~7`, stores the word count at TCB `+0x54`, copies at most 32 name bytes to `+0x34`, then forces byte `+0x53` to NUL. The original `0x417D94` loop has the same 32-byte bound and final NUL store.
- The 18-word initial frame matches the stock stores at `0x41B46E`: base at top-72, `0xFFFFFFFD`, R4-R11 patterns, argument, R1-R3 patterns, R12, literal `0x41B391`, entry, and xPSR `0x01000000`. The raw word at `0x41B534` is `0x41B391` (`DAT_0041B534` in the Ghidra decompilation).
- `thread_register.c` follows stock `0x417E58` field updates: ready-list base `0x20024870 + 20 * priority`, list-head and linked-node offsets, current/highest-priority globals, count, and conditional reschedule. `kernel_runtime.c` initializes 56 normal and five delayed lists; `0x41B53C` confirms sentinel fields at offsets 4, 8, 12, 16, and count at offset 0.
- Critical-section source matches the examined helpers: `0x41B2F8` reads BASEPRI, sets it to 48, and executes DSB/ISB; enter increments nesting; exit decrements and clears BASEPRI only when nesting reaches zero. The zero-nesting underflow path masks interrupts and reaches the invalid store.

The priority-56 boundary is covered by the newer `thread-runtime-compatible/fatal-priority-comparison.json` receipt (PASS1, 398 distinct original trace bytes, locked hash above, current source hashes). It supplies a static-route attribute record at priority 56, observes the original invalid zero store to `0xFFFFFFFF`, and compares the initialized TCB/name/stack and BASEPRI 48 before stopping. The outer wrapper rejects priorities `>=57`, so 56 passes; static initializer `0x417D94` then compares against `0x38`, masks interrupts, and reaches the invalid store before writing priority/frame fields or registering the TCB. The actual exception/HardFault dispatch and resulting hardware behavior are outside the test. Earlier `verify_static.py` coverage (priorities 1, 24, 48, 55) and `verify.py`'s priority-56 case with static-route fields absent do not exercise this boundary; the dedicated receipt now does.

The scatter input confirms that critical-nesting RAM starts at `0x200004C4` with `0xAAAAAAAA`: I decoded exactly the 625-byte input at `0x4341C0`, obtained 1,371 output bytes (SHA-256 `e3bea7ccd46bc324829152b5b5a9069aecce5db243876273084d29bd7d47b843`), and read `AA AA AA AA` at offset `0x4C4`. The integrated runtime receipt reports the same post-registration nesting value and BASEPRI 48. This is the image's initialized state; do not describe it as a zero-initialized counter. The integrated test compares source/original RAM and registers, though the receipt records the post-run value rather than a separate pre-entry field.

Receipt review:

- `thread-runtime-compatible/comparison-first.json` is PASS32 and its source hashes currently match all listed files.
- `thread-runtime-startup-compatible/comparison-first.json` is PASS2 / 1,288 original bytes. Listed code/source hashes match current files; only the Makefile hash differs. It keeps the compiled 72-byte startup table and actual `0x42E39D` callback, with 695 compressed bytes supplied as authenticated fixture inputs. It compares TCB/stack/56 ready lists/five delayed lists/globals and shows `0xAAAAAAAA` nesting and BASEPRI 48.
- `thread-creation-compatible/comparison-first.json` is PASS324; only the Makefile hash differs.
- The saved static and register receipts PASS36 and PASS32, but their source bindings have drifted: `kernel_static.c` and related linker/build files changed after those receipts. The saved lifecycle PASS216 receipt also has a changed `lifecycle.c` hash. Treat those receipts as historical until regenerated against current sources. The current runtime-integrated profile exercises current static creation and register sources on the valid manager path but does not cover name truncation. The dedicated accepted-outer/static-fatal priority-56 receipt covers its own current-source-bound path.

The standalone register profile's critical-section, ready-list initializer, and reschedule helpers are synthetic providers with preseeded circular lists. That scope is explicit in its test harness. The integrated runtime profile instead executes current source helper code against original instructions and compares the initialized arrays; its setup helper at `0x416058` and scheduler-start helper at `0x4160B0` remain synthetic. No actual scheduler switch, PendSV delivery, concurrent execution, hardware behavior, full source coverage, or byte identity is established.

## Heap, timer, scheduler tick/resume, and exception-port follow-up

I reviewed the added `rtos_heap.c`, `timer_service.c`, `scheduler_resume.c`, `scheduler_tick.c`, `thread_select.c`, `exception_entry.S`, and `port_start.c` against the same locked image. Targeted raw disassembly included heap allocate/free/init/insert (`0x419730`, `0x419830`, `0x4198A0`, `0x4198FA`), queue setup (`0x419C9C`, `0x419BE8`, `0x419D68`), deferred resume (`0x418228`), tick (`0x418408`), thread selection (`0x418570`), PendSV (`0x41B31C`), and first task restore (`0x41B2AC`). I found no concrete behavioral discrepancy in the reviewed paths or in the described profiles.

The RTOS heap arithmetic matches the stock structure: start aligns the arena base upward to 8 bytes; the stock initial free payload is `0x13FF0` (81,904 bytes), with the end sentinel and 8-byte header outside that count. Requests round by `16 - (n & 7)`, including 16 bytes for already-8-byte-aligned sizes; splitting is only when the remainder exceeds 16 bytes. The sorted insertion/coalescing logic matches the disassembly. This allocator is distinct from the filesystem TLSF allocator. `thread-heap-compatible/comparison-first.json` is PASS159/496 and compares arena/global state after each operation. Scheduler suspend/resume are synthetic there, and malloc failure stops at the stock hook `0x41B5F6`; the hook's logger/nonreturn implementation is not executed. Invalid/double frees are untested. Dynamic creation's 18/962 profile uses synthetic RTOS allocation; the separate 3/1392 dynamic-plus-real-heap profile executes heap initialization/allocation/split and create/register paths, but does not cover heap exhaustion, deferred ticks, or pending-ready tasks.

The timer source specializes the fresh static queue path. Its queue validation, count/item-size overflow guard, queue fields, 50-item/16-byte timer queue, both list initializers, queue type byte, and timer-thread creation arguments agree with the inspected stock routines. It does not establish queue reuse, wakeup, or general queue semantics. The current port-startup integration PASS2/1958 exercises the fresh queue and timer-thread start; timer configure remains synthetic.

Resume removes the pending-ready and delayed/event nodes, reinserts the TCB in its priority ready list, repairs the unblock cursor, applies accumulated deferred ticks, and requests rescheduling as the stock control flow does. Tick handles suspended accumulation, wrap-list swap with an empty-current-list assertion, delayed wakeups, event-list removal, priority insertion, time slicing when the current ready-list count is at least two, and the existing yield flag. The 288/348 tick profile and 96/502 resume-with-real-tick profile compare these operations against original instructions. They use synthetic coherent lists (including one pending/current task in the resume profile); multiple simultaneous wakeups, concurrent interrupt mutation, and fatal/malformed-list branches are not covered. Tick values are counts, not calibrated milliseconds.

Thread selection's stack watermark checks, history write, highest nonempty ready-priority scan, cursor advancement, and history-ring wrap follow the inspected `0x418570` operations. PendSV and first-task restore assembly match the raw register save/restore order, including conditional S16-S31 save/restore, EXC_RETURN preservation, PSPLIM, PSP, CONTROL, and BASEPRI. The basic PendSV PASS2/236, FP PendSV PASS2/244, and first-restore profiles manually seed valid software/exception frames and stop before architectural exception return. They do not emulate actual exception stacking/unstacking, lazy FP frame creation, interrupt delivery, task execution, or hardware timing. Startup's timer configuration remains synthetic.

For these receipts, I checked source bindings against the current tree: the functional `.c`/`.S` files match; only README/Makefile metadata hashes differ. These results are bounded behavioral comparisons under their stated Unicorn CPU profiles, not source-completeness or byte-identity evidence.

## Timer-startup and SVC-dispatch integration review

I reviewed `verify_timer_integrated.py`, `startup_timer_integrated.ld`, and `verify_svc.py` with their saved receipts. I found no harness mismatch in the exercised success/failure cases. Current receipt results are `thread-timer-startup-compatible/comparison-first.json` PASS2/3,178 and `thread-pendsv-compatible/svc-comparison.json` PASS10/132; both bind the functional source files used by the tests to current hashes (only Makefile metadata differs).

The timer-startup profile extends the actual scatter-table/system-entry/callback route. It clears the prior callback provider set and removes `0x41FD70` from the inherited platform provider cuts, so the source ELF's thread-creation wrapper and allocator initialization are reached. Its linker maps `0x4160FE` to `opencfw_boot_thread_new` and `0x41FD70` to `opencfw_boot_allocator_init`; the manager attributes choose the static route. The source-side table and callback are retained, while the three authenticated compressed streams (22, 625, and 48 bytes) and initial vector SP remain explicit fixtures. The profile checks post-scatter RAM digests, the full compared heap region, manager/idle/timer TCBs and stacks, ready/delayed lists, queue/control blocks, scheduler globals, MMIO fixture state, selected CPU registers, callback publication, and arrival at SVC. The configured handle is fixed at `0x20026AC0`; mode values 0 and 7 are covered.

Provider boundaries remain material: source fill loops use an intercepted fill helper; clock request/release and unused filesystem mutex/printf services are synthetic; allocator logging is reduced to severity/line observations; MMIO state is seeded RAM and cannot establish a timer frequency or peripheral behavior. Although the linker script retains aliases to raw stock routines such as dynamic-thread and platform helpers, the exercised manager, idle, and timer creation attributes use the linked source static path. The result demonstrates this startup fixture chain, not general dynamic-thread behavior, allocator state beyond the compared region, actual callback task execution, hardware timing, or byte identity.

The SVC profile tests both MSP and PSP selection by giving the opposite stack a different immediate, for each of immediates 2, 0, 1, 3, and 255. Immediate 2 enables the FPU and restores the first-task frame; the other tested immediates reach the observed invalid store at `0xFFFFFFFF`. Original/source results compare PSP, CONTROL, BASEPRI, CPACR, and FPCCR, and the successful first-task state agrees. The frames and EXC_RETURN values are synthetic; the test stops before architectural return and does not model hardware stacking, unstacking, exception priorities, or HardFault dispatch. It does not independently compare PSPLIM in the SVC harness, though the separate first-restore receipt does test PSPLIM.
