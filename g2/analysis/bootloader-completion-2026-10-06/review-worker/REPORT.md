# Independent review: Apollo bootloader update-core integration

Review date: 2026-10-06. Scope: `g2/components/bootloader/update_core/` source, module build, and its comparison harness. Target identity checked against `g2/blobs/official/g2-2.2.6.10/ota_s200_bootloader.bin`: 148,599 bytes, SHA-256 `f89a4c4657537cec6bfc572bdb8318866309b90a5d180c4307680d39824167b5`, raw linked base `0x00410000`.

## Assessment

The source is a bounded, source-defined reconstruction of the DFU update-core routines at `0x42D84C` (stream mode), `0x42D890` (CRC validation), `0x42D9F0` (erase visitor), `0x42DA1E` (compare), `0x42DAE8` (program), `0x415758` (memcmp), `0x42E1EC` (CRC), and `0x42DC90` (vector handoff). It is not a complete bootloader source tree or bootable component: paths, log/runtime, filesystem reads, and storage descriptor callback implementations remain explicit external providers. The ELF's absolute provider mappings in `module.ld` are test bindings to existing stock firmware addresses, not provider source implementations.

The original `comparison-first.json` reports a bounded PASS over 4,514 fixtures and 1,208 distinct traced original instruction bytes. The later `comparison-resources-final.json` reports PASS over 4,542 fixtures with the same trace-byte count; its distribution is 4,099 stream-mode inputs, 50 CRC cases, 288 `memcmp`, 7 erase visitor, 13 compare, 42 verify, 42 program, and 1 handoff case. The final artifact includes source-defined ROM string resources and expanded short-read fixtures. My independent emulator rerun covered the earlier 4,514-case ELF only; I did not rerun the final 4,542-case result. These are functional fixture comparisons, not full instruction coverage, exhaustive behavior, complete source, hardware validation, or byte identity.

The Cortex-M55 default build exists (`update-core.elf`, SHA-256 `eca8f363fc82b5b16e2edfc16eaf937bfdefb87a7861af550131998f7c1a0999`) but has no passing run in the supplied comparison. The reported Unicorn unsupported LE instruction `0x1012c` blocks that particular emulator run; the PASS artifact hashes a distinct Cortex-M4 `-O2` ELF (`12016f0e966d9ecfb2fa2861d9352b58d53c1074997cfa0d333e1eb25cdca487`). No evidence here shows that the C source diverges on Cortex-M55; it does mean the passing test cannot be cited as validation of the default M55 binary/profile.

## Findings requiring follow-up

1. **No `memcmp` defect was established in this review.** Reinspection of the stock disassembly at `0x415758` confirms it aligns the left/source pointer bytewise, then checks right-pointer alignment before using words. The source does the same: its leading byte loop aligns the left pointer while size remains, and its word loop is conditional on the right pointer being aligned. The existing fixtures include sizes 4, 5, 7, 8, and 31 across all 16 pointer-alignment pairs, so the word path is exercised where alignment permits. Exact original/source return values are compared. The earlier review claim that this path was untested and that asymmetric alignment differed was incorrect and is withdrawn. The source's typed word accesses still merit ordinary C alignment/aliasing scrutiny, but no mismatch is shown by this evidence.

2. **The default compiler profile is not verified.** `Makefile` defaults to Cortex-M55 `-O2`, while the passing ELF was built as Cortex-M4 `-O2`. Preserve the unsupported instruction finding and obtain a compatible execution strategy, or run the M55 binary with an emulator that supports its emitted instructions. Report the profiles and ELF hashes with any later result. Do not transfer the M4 result to the default M55 build.

3. **Providers and fixture semantics bound compare scope.** The harness intercepts open/prepare/read/close/log/runtime and erase/read/program at fixed stock entry addresses. It does not execute these provider bodies from a complete replacement. Fixtures assume deterministic callback effects and do not model physical flash, filesystem state, concurrency/interruption, callback mutation, cache/flash coherence, or platform failure. This is properly named in result limits. Maintain that boundary in any headline claim.

4. **Short-read behavior is raw compatibility, not robust update semantics.** Both validation and programming log a short read and continue using the entire requested buffer length (CRC/program/compare), leaving stale prior buffer contents in the unread suffix. The final fixtures add zero-byte, positive partial (`3` bytes), and later-read-call (`read_calls[1]=7`) short results across sizes, which cover more of this raw behavior. The implementation appears intentionally faithful to the stock control flow; do not describe this behavior as safely handling short reads.

5. **Handoff scope is appropriately a leaf.** The assembly matches the stock five-instruction sequence exactly: write VTOR, load MSP from vector[0], load reset from vector[1], branch. The fixture captures VTOR/MSP/reset transfer. It does not validate the vector or demonstrate application boot; retain those explicit limits.

6. **Final program log is deliberately partial.** The implementation emits severity/function/line/format with no reproduced variadic values at `0x13C`. The stock code's final call carries incidental values from its loop/error path; current result compares only severity and line. This is a truthful limitation but prevents complete logger-observable equivalence for that branch. Log formats and all other variadic payloads are likewise not compared by the harness.

7. **Malformed or degenerate inputs remain outside the passing domain.** Underflowing encoded lengths, zero storage chunk size, invalid addresses/pointers, and dynamic descriptor mutation can cause wraparound, division-by-zero, nontermination, or invalid memory effects. The result file correctly lists these as not established safe. Preserve raw behavior and keep any hardening separate, as the source comment states.

## Build and byte-identity facts

`make -C g2/components/bootloader/update_core` builds a compact test module linked at `0x10000`, not at the locked raw-image base or original image layout. Its ELF is approximately 3.1 KiB in executable sections, versus the 148,599-byte target. The module linker script maps provider names to absolute addresses inside the original image and places the entry point at the source module. This is an execution/comparison arrangement only. Neither ELF is the original raw payload, and no full payload or EVENOTA bundle rebuild/equality evidence is present. Byte identity is therefore **not achieved or tested**.

Source coverage is also sharply scoped: this module covers update-core logic, while the inventory records 903 functions, 54 decompilation failures, and 245 unclassified catalogue gaps across the complete payload. The present additions do not close startup, scheduler/task flow, filesystem, flash driver, RTOS, runtime, vectors, constants, metadata, padding, or all stored bytes. Do not claim full bootloader-source completeness.

## Conclusion

Accept the addition as a useful partial source implementation with bounded M4 compatibility fixture results and real architectural handoff source. The final comparison now includes positive and later-call short reads. Separately obtain a run for the default M55 ELF. The integration is not a full-source bootloader and makes no defensible byte-identity claim.

## Follow-up review: filesystem integration and startup helpers

This follow-up inspected `comparison-resources-final.json`, the ARM littlefs integration artifact, and startup-helper source plus original bytes. It did not modify source or run another emulator job.

- **Final update-core bindings:** `comparison-resources-final.json` binds original SHA-256 `f89a4c…67b5`, ELF SHA-256 `eb84e29c…0aae4`, and individual SHA-256 values for `update_core.c`, `update_core.h`, `rom_resources.c`, `handoff.S`, `module.ld`, `verify.py`, and `elf_reader.py`. All seven current file hashes match. Thus the 4,542-case result is correctly bound to the current source snapshot. The earlier independent 4,514-case run has a different ELF hash and older source bindings for the linker script/header/verifier; it is not independent confirmation of the final result.
- **Filesystem ARM integration:** `integration-final.json` records 16 actual calls into the compiled source littlefs, file wrappers, update verification/program loop, and file read/seek/close paths. The ELF hash matches the current `filesystem-update.elf`; the ELF attributes identify Cortex-M4/v7E-M rather than the Makefile's default Cortex-M55 profile. Heap allocation, mutex operations, logging/errors, NOR access, and image erase/read/program are intercepted synthetic providers. The synthetic NOR enforces bounds, erase alignment, and one-to-zero programming, but is not physical flash. The artifact properly disclaims IAR build equivalence and hardware behavior. It records ELF identity but no per-source SHA map, so its exact source-input binding is weaker than the final update-core comparison's.
- **Filesystem source scope:** littlefs is copied from the pinned upstream commit and its four source/header hashes match `upstream/SHA256SUMS` and `PROVENANCE.md`. The source glue fixes the recovered 84-byte configuration layout and recovered numeric configuration bytes; integration checks the 64-byte numeric portion at stock address `0x431084`. File wrappers implement mode-to-littlefs flags, read element counts, seek, close, and the stock fixed allocation/mutex boundaries. Exact stock RTOS/heap/NOR provider implementations and exact bootloader littlefs compile configuration remain outside this source closure.
- **Startup helper pseudocode:** comparison-first binds the locked image and source hashes for `initialize.c`, `initialize.h`, `module.ld`, and `verify.py` to the current files. The source matches the control flow of the original Ghidra bodies at `0x415326` and `0x431E38`: relative record input, bit-0-tagged static-base relocation, LZ-style literal/match expansion, size/address zero-table traversal, minimum-word zeroing followed by byte tails, and `record + 3` return. These APIs are deliberately raw and unbounded; truncated/malicious streams and zero-table sizes 1–3 remain outside the claimed-safe domain.
- **Compressed-record bounds:** using the correct raw-image base `0x00410000`, official record inputs are `[0x00434461,0x00434477)` (22 bytes), `[0x004341C0,0x00434431)` (625 bytes), and `[0x00434431,0x00434461)` (48 bytes). All are inside the 148,599-byte image interval `[0x00410000,0x00434477)`; the first ends exactly one byte past the last valid image byte, which is a valid exclusive endpoint, not an out-of-bounds read. The tested decompressed destinations/sizes are `0x40/24`, `0x20000000/1371`, and `0x20080000/4096`. The official zero table at `0x004330DC` contains ranges `0x2000055C/0x26C6C` and `0x20081000/0x74100`, followed by its zero terminator. I found no false out-of-bounds condition in these authenticated records.

The startup comparison currently available to this review is `comparison-first.json` (39 cases, 182 traced original instruction bytes). No whole startup/reset path is established: decompression table production, full reset/FPU/stack setup, RAM-vector producer, scheduler entry, SBL/ROM services, and application boot remain outside the tested helper scope.

## Follow-up review: startup observer and allocator/TLSF

On the parent’s request, I reran the current startup and allocator comparisons sequentially, then reran the filesystem-owned integration with real source TLSF. All output JSON files are isolated under this review-worker directory.

- **Startup independent rerun:** `startup-independent.json` passes 39 cases and 182 traced original bytes. Its current source hashes match `initialize.c`, `initialize.h`, `module.ld`, and `verify.py`; the ELF hash matches `startup-compatible/initialize.elf`. The original instruction/register observer verifies that all bytes in each official compressed input range are consumed, that the final input pointer equals the exact exclusive endpoint, and that each original backreference pointer lies before the current output pointer. All three ranges and decompressed sizes remain as listed above. This directly supports no out-of-bounds read for those authenticated records. An attempted memory-read hook that faults at `0x41538E` is not evidence of a firmware out-of-bounds access; I did not treat it as such. The instruction/register observer passes.
- **Allocator independent rerun:** `allocator-independent.json` passes all 265 cases and 1,994 distinct original instruction bytes against `allocator-compatible/allocator.elf`. Every result includes a full `0x70800`-byte arena hash and control pointer, compared between original and source after each operation. Current hashes match every source file listed by the artifact, including the copied TLSF files and shared freestanding memory routines. The artifact is a Cortex-M4/v7E-M `-O2` test profile, not the default M55 profile or an IAR build.
- **Wrapper/lock semantics:** the C wrappers match the recovered behavior for the tested domain: allocation lock failure returns null without allocating; successful allocation is unlocked; free lock failure leaves the block allocated and unlocked state unchanged; retrying free after lock recovery releases it. This follows the original wrappers at `0x41552C`/`0x415558`. Free is declared `void` in source, while the raw stock body appears to return its incoming R3 value; recovered call sites (`file_services` allocation-failure and close cleanup) ignore that return. The test intentionally drops free's return register, so this is semantic call-site compatibility, not exact ABI/register equivalence. The original allocator initializer decompilation also shows a 64-bit shaped return with a meaningful-looking high word (`0x13`); source returns `uint32_t` zero and tests compare R0 only. Its recovered startup call ignores the return, but exact return-register equivalence is not established.
- **TLSF setup and safety boundary:** the source clears the full arena `[0x20081000,0x200F1800)`, calls pinned v3.1 `tlsf_create_with_pool` with the full `0x70800` byte span, then publishes the returned control pointer at `0x2002718C`, matching the recovered control/pool layout (`0xC74` control prefix and `0x6FB8C` pool argument). The exact upstream source and license hashes match the pinned copy. Assertions are disabled in this candidate build; invalid/double frees, corrupted metadata, and oversized request overflow remain outside the safe-tested domain.
- **Filesystem integration with real TLSF:** independently reran `verify_arm.py --real-allocator` against `filesystem-owned-update.elf`; `filesystem-real-tlsf-independent.json` passes 18 source calls, with 18 allocations/frees, 58 lock/unlock pairs, and `tlsf_check` succeeding at completion. Its full source-hash map matches the integration artifact and its ELF SHA-256. Actual source littlefs, file service, update verification/program loop, and TLSF execute. Mutex, NOR driver, logging/runtime, and image erase/read/program remain synthetic providers over an offline NOR byte model; this still does not prove physical-device behavior, full boot, IAR equivalence, or byte identity.

These results strengthen bounded helper and source-integration evidence only. They do not establish complete bootloader pseudocode/source coverage, full logger argument equivalence, the full reset path, or a byte-identical payload.
