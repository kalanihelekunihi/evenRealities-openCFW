# Independent review: tick expiry and delayed-list rollover

Reviewed the final `comparison-verified.json`, tick verifier, component documentation, and build provenance. I found no blocking issue in the bounded implementation or evidence.

The tick and reset-helper function texts match the pinned FreeRTOS V10.5.1 source at commit `def7d2df2b0506d3d249334974f51e427c17a41c`; the focused tests verify the function hashes, MIT notice, locked stock body, rollover-counter literal, linked providers, and optimized-verifier rejection. The recovered global cells and accessed TCB/list ABI are consistent with the source macros and the earlier independently reviewed ready/resume providers.

The authoritative comparison reports 271 cases and 2,404 unique original instruction bytes. Its firmware and linked ELF hashes match; its five component-manifest hashes are current. The separate build provenance covers all 110 linked inputs and evidence files, including the recompiled resume/list sources, Makefile, build log and link command, compiler/linker versions, effective flags, final result, ELF, and aggregate. I checked every listed path/hash; all are present and current. The selected target uses `-O0` for the new tick/resume/list/provider objects, with the existing O2 profile retained for the other linked objects. This is documented as a simulator semantic-test profile, not the intended firmware build profile or byte-equivalence evidence.

The independent model covers multiple same-deadline and staggered expiries, mixed priorities, linked/unlinked event items, due-at-zero and future tasks on rollover, counter wrap, time slicing, pended-tick replay, suspend/resume composition, and intrusive list state. The final verifier invalidates translation caches only before synthetic top-level calls, symmetrically for stock and source; it performs no call-boundary restart and does not alter instructions or registers. The O2 mismatch and replica are retained as diagnostics and excluded from passing results. I ran `python3 -m unittest g2.tests.test_freertos_tick`; all three focused tests passed.

Remaining limits are clearly stated: task/list/global contents are synthetic; the physical SysTick ISR/startup/frequency, task selection/context switch, full kernel/object lifecycle, and hardware are not exercised. EventGroup unordered-unblock and selected scheduler/WSF/application callbacks remain fixtures. `xTaskIncrementTick` itself executes timeout unlink and ready insertion, while physical interrupt timing and subsequent task execution are unproven.
